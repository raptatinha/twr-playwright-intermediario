Seção 01 · 20 min

🎯 Alinhamento e Boas Práticas Essenciais

Revisão rápida da estrutura
  • Organização de pastas: tests/, pages/, fixtures/
  • Separação clara de responsabilidades
  • Convenções de nomenclatura
  • playwright.config.ts como ponto central
Locators recomendados
  • getByRole() — acessível e resiliente
  • getByTestId() — quando role não basta
  • getByLabel(), getByPlaceholder()
  • getByText() — conteúdo visível
  • Evite css e xpath frágeis
⚠️ Anti-patterns comuns: waitForTimeout(), seletores frágeis (.btn-primary > span:nth-child(2)), lógica de negócio dentro do teste. 
// ✅ Bons locators
page.getByRole('button',
  { name: 'Salvar' });
page.getByTestId('cart-total');
page.getByLabel('E-mail');

// ❌ Anti-patterns
page.locator(
  '.container > div:nth-child(3) a');
await page.waitForTimeout(3000);

// ❌ Lógica dentro do teste
if (await page.isVisible('.modal')) {
  await page.click('.close');
}

// ✅ Estrutura recomendada
meu-projeto/
├── tests/        // specs
├── pages/        // page objects
├── fixtures/     // custom fixtures
├── utils/        // helpers
└── playwright.config.ts

Seção 02 · 25 min

🏗️ Page Objects na Prática

O problema
  • Testes duplicados e difíceis de manter
  • Mudança na UI = alterar dezenas de arquivos
  • Locators espalhados por toda a suíte
  • Testes longos e difíceis de ler
Estrutura simples de Page Object
  • Uma classe por página/componente
  • Locators como propriedades privadas
  • Métodos públicos = ações do usuário
  • Constructor recebe Page
💡 Quando NÃO usar: Testes simples de uma página só, protótipos rápidos, ou suítes muito pequenas (< 5 testes). 
// pages/login.page.ts
export class LoginPage {
  private emailInput: Locator;
  private passwordInput: Locator;
  private submitButton: Locator;

  constructor(private page: Page) {
    this.emailInput = page
      .getByLabel('E-mail');
    this.passwordInput = page
      .getByLabel('Senha');
    this.submitButton = page
      .getByRole('button',
        { name: 'Entrar' });
  }

  async login(email, senha) {
    await this.emailInput
      .fill(email);
    await this.passwordInput
      .fill(senha);
    await this.submitButton.click();
  }
}

Seção 02 · Page Objects

Separar Ações vs Validações

Ações vs Validações
  • Ações: métodos que interagem com a UI
  • Validações: métodos com expect / assertions
  • Prefixe validações: assertSuccess(), verifyMessage()
  • Ações retornam void ou a próxima page
Boas práticas de POM
  • Máximo ~200 linhas por arquivo
  • Sufixo Page: LoginPage, CheckoutPage
  • Nomeie locators com tipo: submitBtn, emailInput
  • POMs para componentes: HeaderComponent
// pages/checkout.page.ts
export class CheckoutPage {
  constructor(private page: Page) {}

  // ── Ações ──
  async fillAddress(address: string) {
    await this.page
      .getByLabel('Endereço')
      .fill(address);
  }

  async submitOrder() {
    await this.page
      .getByRole('button',
        { name: 'Finalizar' })
      .click();
  }

  // ── Validações ──
  async assertOrderConfirmed() {
    await expect(this.page
      .getByText('Pedido confirmado'))
      .toBeVisible();
  }

  async assertTotal(value: string) {
    await expect(this.page
      .getByTestId('order-total'))
      .toHaveText(value);
  }
}

🧩 Fixtures e Reutilização de Setup

O que são Fixtures
  • Setup compartilhado + injeção de dependências
  • Substituem beforeEach repetitivos
  • Antes de use() = setup, depois = teardown
  • Podem acelerar execução significativamente
Test vs Worker scope
  • Test scope: nova instância por teste (padrão)
  • Worker scope: compartilhada entre testes do worker
  • Worker = ideal para setup custoso (DB, auth)
  • { scope: 'worker' } na definição
// fixtures/pages.fixture.ts
import { test as base }
  from '@playwright/test';
import { LoginPage }
  from '../pages/login.page';

type MyFixtures = {
  loginPage: LoginPage;
};

export const test =
  base.extend<MyFixtures>({
  loginPage: async ({ page }, use) => {
    // Setup
    const lp = new LoginPage(page);
    await lp.goto();
    // Injeta no teste
    await use(lp);
    // Teardown (após o teste)
  },
});

// No spec — uso limpo
import { test }
  from '../fixtures/pages.fixture';

test('login com sucesso',
  async ({ loginPage }) => {
  await loginPage.login(
    'user@email.com', 'senha123');
});

Seção 03 · Fixtures

Compartilhando Dados e Custom Fixtures

Compartilhando dados entre testes
  • Fixtures podem gerar dados e injetá-los
  • Worker fixture = mesmo dado para todo o worker
  • Ideal para tokens, usuários criados via API
  • Cleanup automático no teardown
Custom fixtures avançadas
  • Compor múltiplas fixtures com extend
  • Fixture que depende de outra fixture
  • Fixtures com opções configuráveis
  • Fixtures para API requests
⚠️ Cuidado: Uma fixture "base" que instancia tudo carrega na memória objetos desnecessários. Prefira fixtures focadas. 
// Worker-scoped fixture
export const test =
  base.extend<{}, { apiToken: string }>({
  apiToken: [async ({}, use) => {
    // Roda 1x por worker
    const token = await
      getAuthToken();
    await use(token);
  }, { scope: 'worker' }],
});

// Fixture com dependência
export const test =
  base.extend<{
  dashboardPage: DashboardPage;
}>({
  dashboardPage: async (
    { page, apiToken }, use
  ) => {
    await page.goto('/dashboard');
    const dp = new
      DashboardPage(page);
    await use(dp);
  },
});

🔐 Autenticação e Gerenciamento de Estado

storageState
  • Login uma única vez, reutilizar sessão
  • Salva cookies + localStorage em JSON
  • Cada teste começa já autenticado
  • Configurado via project setup + dependencies
Cookies e sessão
  • storageState salva cookies e localStorage
  • Cookies expiram — setup re-executa se necessário
  • Não salva sessionStorage (usar workaround)
  • Adicione playwright/.auth/ ao .gitignore
Ambientes diferentes
  • Variáveis de ambiente para URLs e credenciais
  • baseURL por project ou .env
  • Setup diferente por ambiente (local, staging, prod)
// playwright.config.ts — auth setup
export default defineConfig({
  projects: [
    {
      name: 'setup',
      testMatch: '**/*.setup.ts',
    },
    {
      name: 'chromium',
      use: {
        storageState:
          'playwright/.auth/session.json',
      },
      dependencies: ['setup'],
    },
  ],
});

// tests/setup/auth.setup.ts
setup('fazer login',
  async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('E-mail')
    .fill('user@email.com');
  await page.getByLabel('Senha')
    .fill('senha123');
  await page.getByRole('button',
    { name: 'Entrar' }).click();
  await page.context()
    .storageState({ path: authFile });
});

Seção 04 · Auth

Login uma vez para toda a suíte

Login uma vez, reutilizar sessão
  • Project setup roda antes dos demais
  • Outros projects dependem do setup
  • Via UI: simula fluxo real (mais lento)
  • Via API: chama endpoint direto (recomendado)
Múltiplos perfis
  • Setup separado para admin e user
  • Projects: 'admin-tests', 'user-tests'
  • Cada um com seu storageState
  • Útil para permissões e aprovação
⚠️ Cuidado: Adicione playwright/.auth/ ao .gitignore — os JSONs contêm tokens sensíveis. 
// Login via API (mais rápido)
setup('fazer login via API',
  async ({ }) => {
  const ctx = await request
    .newContext();
  await ctx.post(
    'https://exemplo.com/api/login',
    { data: {
      email: 'user@email.com',
      password: 'senha123',
    }});
  await ctx.storageState(
    { path: authFile });
  await ctx.dispose();
});

// Config — múltiplos perfis
projects: [
  { name: 'setup-admin',
    testMatch: '**/admin.setup.ts' },
  { name: 'setup-user',
    testMatch: '**/user.setup.ts' },
  { name: 'admin-tests',
    use: { storageState:
      'playwright/.auth/admin.json' },
    dependencies: ['setup-admin'] },
  { name: 'user-tests',
    use: { storageState:
      'playwright/.auth/user.json' },
    dependencies: ['setup-user'] },
]

Seção 05 · 20 min

👥 Fluxos Complexos e Múltiplos Contextos

Multi-page e Popups
  • page.waitForEvent('popup') — novas abas
  • Cada aba é uma Page independente
  • Útil para OAuth, links target="_blank"
  • Sem window handle como Selenium
Multi-step flows
  • Checkout, onboarding, wizards
  • test.describe.serial para sequência
  • Cada step pode ser um teste separado
  • Compartilhar estado via fixtures
Context vs Page
  • Context: isolamento completo (cookies, storage)
  • Page: aba dentro de um context
  • Multi-user = múltiplos contexts
// Multi-user — dois usuários
const ctx1 = await browser
  .newContext();
const ctx2 = await browser
  .newContext();
const userA = await ctx1
  .newPage();
const userB = await ctx2
  .newPage();

await userA.goto('/chat');
await userB.goto('/chat');
await userA.getByLabel('Mensagem')
  .fill('Olá!');
await userA.getByRole('button',
  { name: 'Enviar' }).click();
await expect(userB
  .getByText('Olá!')).toBeVisible();

// Multi-tab — capturar popup
const [popup] = await Promise
  .all([
  page.waitForEvent('popup'),
  page.getByText('Abrir em nova aba')
    .click(),
]);
await expect(popup)
  .toHaveURL(/nova-pagina/);

Seção 06 · 20 min

🌐 Network Interception e API

Interceptar requests (route)
  • page.route() — interceptar requests
  • route.fulfill() — retornar mock
  • route.abort() — bloquear requests
  • route.continue() — deixar passar
Mockar respostas
  • Evita dependência de backend instável
  • Testa cenários de erro (500, timeout)
  • Testa edge cases (lista vazia, dados grandes)
  • Acelera testes removendo chamadas lentas
💡 Dica: Bloqueie analytics e third-party scripts para testes mais rápidos e estáveis. 
// Mock de API — retornar dados
await page.route(
  '**/api/products',
  async (route) => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify(
      [{ id: 1, name: 'Produto Mock' }]),
  });
});

// Simular erro do servidor
await page.route(
  '**/api/checkout',
  (route) => route.fulfill({
    status: 500,
    body: 'Internal Server Error',
  }));

// Bloquear analytics
await page.route(
  '**/analytics/**',
  (route) => route.abort());

// Esperar resposta real
const resp = await page
  .waitForResponse('**/api/users');
expect(resp.status()).toBe(200);

Seção 06 · API

Testes de API com request

Testes de API básicos
  • request fixture nativa do Playwright
  • Não precisa de browser — execução rápida
  • GET, POST, PUT, DELETE
  • Validar status, body, headers
Evitar dependência de backend
  • Use mocks para testes de UI
  • Use API real para testes de API
  • Combine: crie dados via API, teste via UI
  • Cleanup via API no teardown
// Teste de API direto
import { test, expect }
  from '@playwright/test';

test('GET /api/users retorna lista',
  async ({ request }) => {
  const resp = await request
    .get('/api/users');
  expect(resp.status()).toBe(200);
  const body = await resp.json();
  expect(body.length)
    .toBeGreaterThan(0);
});

test('POST /api/tags cria tag',
  async ({ request }) => {
  const resp = await request
    .post('/api/tags', {
    data: { name: 'Nova Tag' },
  });
  expect(resp.status()).toBe(201);
  const tag = await resp.json();
  expect(tag.name).toBe('Nova Tag');
});

// Cleanup no teardown
test.afterEach(async ({ request }) => {
  await request
    .delete(`/api/tags/${tagId}`);
});

Seção 07 · 15 min

📦 Lidando com Dados

Estratégias para dados de teste
  • .env — variáveis de ambiente (credenciais, URLs)
  • Dicionário JSON — dados estáticos centralizados
  • APIs — criar/limpar dados via endpoints
  • Mock — dados falsos para testes isolados
Boas práticas com dados
  • Dados únicos por teste (evitar conflitos paralelos)
  • Nunca dependa de dados pré-existentes no banco
  • Cleanup: crie no setup, delete no teardown
  • Use Faker.js para dados realistas
💡 Exemplos no repo: data-exemple-1/e2e (dicionário JSON), data-exemple-2/e2e (APIs), data-example-3/e2e (mock). 
// .env
BASE_URL=https://staging.app.com
ADMIN_EMAIL=admin@test.com
ADMIN_PASS=secretpass

// data/tags.json — dicionário
{
  "validTag": { "name": "Playwright" },
  "emptyTag": { "name": "" }
}

// Criar dados via API (setup)
test.beforeEach(async ({ request }) => {
  const resp = await request
    .post('/api/tags', {
    data: { name: `tag-${Date.now()}` },
  });
  tagId = (await resp.json()).id;
});

// Cleanup (teardown)
test.afterEach(async ({ request }) => {
  await request
    .delete(`/api/tags/${tagId}`);
});

💬 Integrações com Slack

Por que integrar com Slack?
  • Notificação automática quando testes falham
  • Visibilidade para todo o time
  • Resultado detalhado no canal
  • Integra com CI/CD (GitHub Actions, etc.)
Como funciona
  • Custom reporter ou script pós-execução
  • Webhook do Slack para enviar mensagens
  • Incluir: total, passed, failed, duração
  • Link para o relatório HTML
💡 Referências:
playwrightsolutions.com — Slack messages
playwrightsolutions.com — Test results to Slack 
// reporter/slack-reporter.ts
import { Reporter }
  from '@playwright/test/reporter';

class SlackReporter
  implements Reporter {

  async onEnd(result) {
    const message = {
      text: `🎭 Testes: ${result.status}
✅ Passed: ${result.passed}
❌ Failed: ${result.failed}
⏱️ Duração: ${result.duration}ms`,
    };

    await fetch(
      process.env.SLACK_WEBHOOK_URL,
      {
        method: 'POST',
        headers: {
          'Content-Type':
            'application/json',
        },
        body: JSON.stringify(message),
      }
    );
  }
}

// playwright.config.ts
reporter: [
  ['html'],
  ['./reporter/slack-reporter.ts'],
],
