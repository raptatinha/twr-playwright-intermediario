Alinhamento e Boas Práticas Essenciais

Fundamentos Boas Práticas
Estrutura de um projeto Playwright
  • tests/ — arquivos .spec.ts com os cenários de teste
  • pages/ — Page Objects para encapsular locators e ações
  • fixtures/ — setup reutilizável e injeção de dependências
  • utils/ — helpers, dados, constantes
  • playwright.config.ts — configuração centralizada na raiz
  • Comece simples e refatore à medida que o projeto cresce
Locators recomendados
  • getByRole() — preferido. Baseado em acessibilidade, resiliente a mudanças de UI
  • getByTestId() — para elementos sem role semântico acessível
  • getByLabel() — para inputs com labels associados
  • getByText() — para textos visíveis na tela
  • getByPlaceholder() — para inputs com placeholder
  • Documentação: playwright.dev/docs/locators
Anti-patterns comuns
  • waitForTimeout() — nunca use! Faz um "pause" fixo, torna o teste lento e instável
  • Seletores frágeis — evite CSS com classes geradas (.btn-x7k2), XPath longo, IDs dinâmicos
  • Lógica dentro do teste — não coloque if/else, for, try/catch nos specs. Extraia para helpers ou Page Objects
  • Dependência entre testes — cada teste deve funcionar isoladamente
  • Dados fixos compartilhados — gera conflitos em paralelo. Use dados únicos por teste
Dicas para projetos reais
  • Use playwright.dev como referência #1 — é sempre a fonte mais atualizada
  • Ative notificações de releases no GitHub para acompanhar novidades
  • Prefira expect com auto-retry em vez de esperas manuais
  • Configure forbidOnly: !!process.env.CI para evitar .only na pipeline
  • Use trace: 'on-first-retry' como padrão — diagnóstico sem impacto em performance
// ❌ Anti-patterns — EVITE isso
await page.waitForTimeout(3000); // Nunca use!
await page.locator('.btn-x7k2 > div:nth-child(3)').click(); // Seletor frágil
await page.locator('xpath=//div[@class="container"]/form/button[2]').click(); // XPath longo

// ✅ Boas práticas — USE isso
await page.getByRole('button', { name: 'Enviar' }).click(); // Role-based
await page.getByTestId('submit-form').click(); // Test ID
await page.getByLabel('E-mail').fill('user@email.com'); // Label

// ❌ Lógica dentro do teste
test('fluxo com condicionais', async ({ page }) => {
  const isVisible = await page.getByText('Banner').isVisible();
  if (isVisible) { /* ... */ } // Não faça isso no spec!
});

// ✅ Teste direto e claro
test('banner é exibido na home', async ({ page }) => {
  await page.goto('/');
  await expect(page.getByText('Banner')).toBeVisible();
});
💡 Para lembrar

O Playwright já implementa auto-waiting na maioria das ações. Não tente reinventar a espera — use assertions com auto-retry (expect) e confie no framework. Consulte a tabela de actionability para entender quais checks cada ação faz automaticamente.

⚠️ Seletores frágeis quebram sem aviso

Seletores baseados em classes CSS geradas, posição no DOM ou estrutura HTML mudam a cada deploy. Use getByRole(), getByTestId() e getByLabel() — eles são resilientes a mudanças de layout e refatorações de frontend.

Page Objects na Prática

Arquitetura Manutenção
O problema: testes duplicados e difíceis de manter
  • Sem Page Object, locators e ações são repetidos em vários specs
  • Quando a UI muda, você precisa alterar N arquivos em vez de 1
  • Testes ficam longos, difíceis de ler e propensos a inconsistências
  • Nomes de variáveis e seletores ficam inconsistentes entre specs
  • Dificulta onboarding de novos membros no time
Estrutura simples de Page Object
  • Uma classe por página (ou componente) da aplicação
  • Constructor: recebe page e define todos os locators
  • Métodos de ação: goto(), login(), fillForm() — executam interações
  • Métodos de assert: assertSuccess(), assertError() — validam estado
  • Nomeie com sufixo Page: LoginPage, CheckoutPage
  • Documentação: playwright.dev/docs/pom
Separar ações vs validações
  • Ações (métodos que fazem coisas): login(), addToCart(), submitForm()
  • Validações (métodos que verificam): assertLoginSuccess(), assertErrorVisible()
  • Prefixe validações com assert para facilitar o autocomplete
  • Métodos de ação não devem conter assertions — mantenha responsabilidades separadas
  • Exceção: um await expect(page).toHaveURL() dentro de goto() pode ser aceitável como guarda
Quando NÃO usar Page Object
  • Projetos muito pequenos (1-5 specs) — adiciona complexidade desnecessária
  • Testes de API puros — não há página para encapsular
  • Testes exploratórios ou POCs — velocidade é prioridade
  • Quando cada teste é completamente diferente — não há reutilização real
  • Regra: comece sem POM, e refatore quando perceber repetição
// pages/login.page.ts — Page Object com separação ações vs validações
import { type Page, type Locator, expect } from '@playwright/test';

export class LoginPage {
  private emailInput: Locator;
  private passwordInput: Locator;
  private submitButton: Locator;
  private errorLabel: Locator;

  constructor(private page: Page) {
    this.emailInput = page.getByLabel('E-mail');
    this.passwordInput = page.getByLabel('Senha');
    this.submitButton = page.getByRole('button', { name: 'Entrar' });
    this.errorLabel = page.getByTestId('login-error');
  }

  // ── Ações ──
  async goto() {
    await this.page.goto('/login');
  }

  async login(email: string, senha: string) {
    await this.emailInput.fill(email);
    await this.passwordInput.fill(senha);
    await this.submitButton.click();
  }

  // ── Validações ──
  async assertLoginSuccess() {
    await expect(this.page).toHaveURL(/dashboard/);
  }

  async assertErrorVisible(message: string) {
    await expect(this.errorLabel).toContainText(message);
  }
}
// tests/login.spec.ts — Teste limpo usando Page Object
import { test } from '@playwright/test';
import { LoginPage } from '../pages/login.page';

test('login com sucesso', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login('user@email.com', 'senha123');
  await loginPage.assertLoginSuccess();
});

test('exibe erro com credenciais inválidas', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login('user@email.com', 'errada');
  await loginPage.assertErrorVisible('Credenciais inválidas');
});
💡 Para lembrar

Page Object não é só para páginas inteiras. Crie Page Objects para componentes reutilizáveis como menus, modais ou barras de navegação — ex.: TopMenuPage com o método logout(). Comece simples e divida à medida que o projeto cresce.

🏠 Para praticar em casa
  • Crie um Page Object para uma página de cadastro com métodos goto(), register() e assertRegistrationSuccess()
  • Refatore um teste existente para usar Page Object e compare a legibilidade
  • Crie um Page Object para um componente (ex.: menu de navegação) e use-o em dois specs

Fixtures e Reutilização de Setup

Arquitetura Performance
O que são Fixtures
  • Fixtures são um mecanismo nativo do Playwright para compartilhar setup entre testes
  • Substituem beforeEach repetitivos — o código roda antes do teste e é limpo automaticamente
  • Gerenciam o ciclo de vida: page objects, dados, contextos de browser
  • Tudo antes do use() é setup, tudo depois é teardown
  • O Playwright já possui fixtures built-in: page, context, browser, request
  • Documentação: playwright.dev/docs/test-fixtures
Test scope vs Worker scope
  • Test scope (padrão): criada e destruída para cada teste. Isolamento total
  • Worker scope: criada uma vez por worker e compartilhada entre todos os testes daquele worker
  • Use worker scope para recursos caros: conexão de banco, autenticação, dados estáticos
  • Use test scope para page objects, dados que mudam entre testes
  • Defina o scope com { scope: 'worker' } no segundo argumento da fixture
Compartilhando dados entre testes
  • Fixtures permitem passar dados preparados diretamente para os testes
  • Ex.: uma fixture que cria um usuário via API e passa os dados para o teste
  • Evita duplicar setup em beforeEach de vários specs
  • Fixtures podem depender umas das outras — o Playwright resolve a cadeia automaticamente
Custom Fixtures — quando criar
  • Quando múltiplos specs instanciam os mesmos Page Objects
  • Quando o setup envolve chamadas de API ou criação de dados
  • Quando quer encapsular login + navegação como pré-condição
  • Mantenha fixtures focadas — uma por área em vez de uma fixture gigante
  • Exporte test e expect do arquivo de fixture
// fixtures/app.fixture.ts — Custom fixture com page objects
import { test as base } from '@playwright/test';
import { LoginPage } from '../pages/login.page';
import { DashboardPage } from '../pages/dashboard.page';

type AppFixtures = {
  loginPage: LoginPage;
  dashboardPage: DashboardPage;
};

export const test = base.extend<AppFixtures>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await use(loginPage);
    // teardown (opcional): logout, limpar dados, etc.
  },

  dashboardPage: async ({ page }, use) => {
    await use(new DashboardPage(page));
  },
});

export { expect } from '@playwright/test';
// fixtures/data.fixture.ts — Fixture com worker scope para dados compartilhados
import { test as base } from '@playwright/test';

type WorkerFixtures = {
  apiToken: string;
};

export const test = base.extend<{}, WorkerFixtures>({
  apiToken: [async ({}, use) => {
    // Setup: obter token uma vez por worker
    const response = await fetch('https://api.example.com/auth', {
      method: 'POST',
      body: JSON.stringify({ user: 'test', pass: 'test' }),
    });
    const { token } = await response.json();
    await use(token);
    // Teardown: revogar token
  }, { scope: 'worker' }],
});
// tests/dashboard.spec.ts — Usando a fixture customizada
import { test, expect } from '../fixtures/app.fixture';

test('login com sucesso via fixture', async ({ loginPage }) => {
  // loginPage já navegou para /login (fixture fez o setup)
  await loginPage.login('user@email.com', 'senha123');
  await loginPage.assertLoginSuccess();
});

test('dashboard exibe dados', async ({ dashboardPage }) => {
  await expect(dashboardPage.welcomeLabel).toBeVisible();
});
💡 Como a Fixture funciona

A fixture executa tudo que está antes de use() como setup, passa o objeto para o teste, e executa tudo depois de use() como teardown. O Playwright gerencia isso de forma otimizada — diferente de beforeEach que recria tudo a cada teste.

⚠️ Cuidado com fixtures grandes

Uma fixture "base" que instancia todos os page objects de uma vez carrega tudo na memória mesmo quando o teste precisa de apenas um. Crie fixtures por área — ex.: auth.fixture.ts, checkout.fixture.ts — para manter o projeto escalável.

🏠 Para praticar em casa
  • Crie uma fixture que instancia um Page Object e navega para a página
  • Crie uma fixture com worker scope que gera um token de API reutilizável
  • Refatore um beforeEach repetitivo para usar fixture

Autenticação e Gerenciamento de Estado

Prática Otimização
storageState — login reutilizável
  • Permite fazer login uma única vez e reutilizar a sessão em todos os testes
  • Salva cookies e localStorage em um arquivo JSON
  • Cada teste começa já autenticado — muito mais rápido
  • Configurado via project setup com dependencies no config
  • O JSON armazena apenas cookies e origins (localStorage)
  • Documentação: playwright.dev/docs/auth
Login uma vez para toda a suíte
  • Crie um arquivo auth.setup.ts que faz login e salva o estado
  • Configure um project 'setup' que roda antes dos outros
  • Projetos de teste usam dependencies: ['setup'] e storageState
  • Login via API é mais rápido e estável que login via UI
  • Não use globalSetup (legado) — prefira a abordagem com projects
Cookies e sessão
  • storageState captura cookies de autenticação e dados do localStorage
  • Não captura sessão server-side — se o servidor invalida, o setup precisa rodar novamente
  • Cookies têm data de expiração — configure TTL adequado no backend para testes
  • Adicione playwright/.auth/ ao .gitignore — os JSONs contêm tokens
Ambientes diferentes
  • Use variáveis de ambiente para URLs e credenciais por ambiente
  • baseURL pode ser dinâmica: process.env.BASE_URL || 'http://localhost:3000'
  • Crie arquivos .env.staging, .env.production com dados específicos
  • Múltiplos perfis: admin.json, user.json com projects separados
  • Documentação: playwright.dev/docs/auth#multiple-signed-in-roles
// playwright.config.ts — setup de autenticação com projects
import { defineConfig } from '@playwright/test';

export default defineConfig({
  projects: [
    {
      name: 'setup',
      testDir: './tests/setup',
      testMatch: '**/*.setup.ts',
    },
    {
      name: 'chromium',
      use: {
        browserName: 'chromium',
        storageState: 'playwright/.auth/session.json',
      },
      dependencies: ['setup'],
    },
  ],
});
// tests/setup/auth.setup.ts — Login via API (recomendado)
import { test as setup, request } from '@playwright/test';

const authFile = 'playwright/.auth/session.json';

setup('fazer login via API', async ({}) => {
  const apiContext = await request.newContext();
  const response = await apiContext.post('https://exemplo.com/api/login', {
    data: {
      email: process.env.TEST_USER_EMAIL,
      password: process.env.TEST_USER_PASSWORD,
    },
  });
  if (!response.ok()) throw new Error('Falha ao fazer login via API');
  await apiContext.storageState({ path: authFile });
  await apiContext.dispose();
});
// playwright.config.ts — múltiplos perfis (admin + user)
export default defineConfig({
  projects: [
    { name: 'setup-admin', testMatch: '**/admin.setup.ts' },
    { name: 'setup-user', testMatch: '**/user.setup.ts' },
    {
      name: 'admin-tests',
      use: { storageState: 'playwright/.auth/admin.json' },
      dependencies: ['setup-admin'],
    },
    {
      name: 'user-tests',
      use: { storageState: 'playwright/.auth/user.json' },
      dependencies: ['setup-user'],
    },
  ],
});
💡 Para lembrar

Login via API é o método mais recomendado para projetos reais — é rápido, estável e não depende da UI de login funcionar. Reserve o teste de login via UI para um único spec dedicado. Use storageState para todos os outros testes que precisam de usuário autenticado.

⚠️ Nunca commite arquivos de autenticação

Adicione playwright/.auth/ ao .gitignore. Os JSONs de storageState contêm tokens de sessão reais. Use variáveis de ambiente (.env) para credenciais — nunca hardcode senhas no código.

Fluxos Complexos e Múltiplos Contextos

Avançado Prática
Multi-page e Popups
  • O Playwright intercepta novas abas e popups automaticamente
  • Use page.waitForEvent('popup') para capturar a nova aba
  • Cada aba é uma Page independente — mesmos métodos de interação
  • Útil para: OAuth, links que abrem em nova aba, janelas de pagamento
  • Não precisa de window handle como em Selenium
  • Documentação: playwright.dev/docs/pages
Multi-step flows (checkout, onboarding)
  • Use test.describe.serial() quando steps dependem um do outro
  • Prefira preparar dados via API e testar apenas a etapa que interessa
  • Não crie um teste enorme — divida em steps menores com describe.serial
  • Use storageState ou API para pular etapas anteriores
  • Valide cada step isoladamente quando possível
Multi-user (conceito)
  • Crie múltiplos browser contexts no mesmo teste
  • Cada contexto tem seus próprios cookies, sessão e storage
  • Ideal para testar: chat em tempo real, permissões, aprovações
  • Ambos os usuários rodam no mesmo browser (sem custo extra)
  • Use browser.newContext() para criar contextos independentes
Context vs Page
  • Browser Context = sessão isolada (cookies, storage, permissions)
  • Page = uma aba dentro de um context
  • Um context pode ter múltiplas pages (abas)
  • Pages no mesmo context compartilham cookies e sessão
  • Use contextos separados para simular usuários diferentes
  • Use pages separadas para simular múltiplas abas do mesmo usuário
// Multi-user — dois usuários simultâneos no mesmo teste
test('chat entre dois usuários', async ({ browser }) => {
  const context1 = await browser.newContext();
  const context2 = await browser.newContext();
  const userA = await context1.newPage();
  const userB = await context2.newPage();

  await userA.goto('/chat');
  await userB.goto('/chat');
  await userA.getByLabel('Mensagem').fill('Olá!');
  await userA.getByRole('button', { name: 'Enviar' }).click();
  await expect(userB.getByText('Olá!')).toBeVisible();
});
// Multi-tab — capturar popup/nova aba
test('link abre em nova aba', async ({ page }) => {
  const [popup] = await Promise.all([
    page.waitForEvent('popup'),
    page.getByText('Abrir em nova aba').click(),
  ]);
  await expect(popup).toHaveURL(/nova-pagina/);
  await expect(popup.getByRole('heading')).toBeVisible();
});
// Multi-step flow — checkout com describe.serial
test.describe.serial('fluxo de checkout', () => {
  test('adicionar produto ao carrinho', async ({ page }) => {
    await page.goto('/products');
    await page.getByRole('button', { name: 'Adicionar' }).click();
    await expect(page.getByTestId('cart-count')).toHaveText('1');
  });

  test('preencher endereço', async ({ page }) => {
    await page.goto('/checkout/address');
    await page.getByLabel('CEP').fill('01310-100');
    await page.getByRole('button', { name: 'Continuar' }).click();
  });

  test('finalizar compra', async ({ page }) => {
    await page.getByRole('button', { name: 'Finalizar' }).click();
    await expect(page.getByText('Pedido confirmado')).toBeVisible();
  });
});
💡 Para lembrar

Context = sessão isolada (cookies, storage). Page = aba dentro de um context. Use contextos diferentes para simular usuários diferentes. Use pages diferentes (no mesmo context) para simular múltiplas abas do mesmo usuário.

🏠 Para praticar em casa
  • Crie um teste com dois contextos simulando dois usuários acessando a mesma página
  • Teste um link que abre em nova aba e valide o conteúdo da popup
  • Crie um fluxo multi-step com describe.serial

Network Interception e API

Avançado Mocks
Interceptar requests (route)
  • page.route() permite interceptar e modificar requisições de rede
  • route.fulfill() — retorna dados mockados para o browser
  • route.abort() — bloqueia uma requisição (analytics, imagens, etc.)
  • route.continue() — deixa a requisição prosseguir (com headers modificados)
  • Pode criar uma classe NetworkInterceptor reutilizável
  • Documentação: playwright.dev/docs/mock
Mockar respostas
  • Retorne dados fixos para isolar o frontend do backend
  • Simule erros (500, 404, timeout) para testar tratamento de falhas
  • Simule respostas lentas para testar loading states
  • Útil para testar cenários difíceis de reproduzir (ex.: servidor fora do ar)
  • Mantenha arquivos JSON com mocks para reutilizar entre testes
Evitar dependência de backend
  • Mocks permitem rodar testes de frontend sem backend disponível
  • Útil em CI quando o backend está em outro time/pipeline
  • Combine: testes com mock (isolamento) + testes E2E sem mock (integração real)
  • Use mocks para cenários de erro que são difíceis de gerar no backend
Testes de API com request
  • Playwright tem suporte nativo a testes de API com request fixture
  • Use request.get(), request.post(), etc. sem precisar de browser
  • Ideal para: criar dados, validar backend, setup de testes
  • Mais rápido que testes via UI — não precisa renderizar página
  • Documentação: playwright.dev/docs/api-testing
// Interceptar e mockar uma API
await page.route('**/api/products', async (route) => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify([
      { id: 1, name: 'Produto Mock', price: 29.90 },
      { id: 2, name: 'Outro Produto', price: 49.90 },
    ]),
  });
});

// Simular erro 500
await page.route('**/api/products', async (route) => {
  await route.fulfill({ status: 500, body: 'Internal Server Error' });
});

// Bloquear requisições desnecessárias
await page.route('**/*.{png,jpg,jpeg}', (route) => route.abort());
await page.route('**/analytics/**', (route) => route.abort());
// NetworkInterceptor — classe reutilizável para interceptações
import { type Page } from '@playwright/test';

export class NetworkInterceptor {
  constructor(private page: Page) {}

  async mockProducts(products: any[]) {
    await this.page.route('**/api/products', async (route) => {
      await route.fulfill({
        status: 200,
        contentType: 'application/json',
        body: JSON.stringify(products),
      });
    });
  }

  async mockError(url: string, status: number) {
    await this.page.route(url, async (route) => {
      await route.fulfill({ status });
    });
  }

  async blockAnalytics() {
    await this.page.route('**/analytics/**', (route) => route.abort());
  }
}
// Testes de API com request fixture (sem browser)
import { test, expect } from '@playwright/test';

test('API retorna lista de produtos', async ({ request }) => {
  const response = await request.get('/api/products');
  expect(response.status()).toBe(200);
  const data = await response.json();
  expect(data.length).toBeGreaterThan(0);
});

test('criar produto via API', async ({ request }) => {
  const response = await request.post('/api/products', {
    data: { name: 'Novo Produto', price: 99.90 },
  });
  expect(response.status()).toBe(201);
});
💡 Para lembrar

Mocks são poderosos, mas use com moderação. Testes com mock validam o frontend isoladamente — mantenha também testes E2E sem mock para garantir a integração real. Centralize interceptações comuns em uma classe NetworkInterceptor reutilizável.

🏠 Para praticar em casa
  • Crie um teste que intercepta uma API e retorna dados mockados
  • Simule um erro 500 e verifique se a mensagem de erro aparece na UI
  • Crie uma classe NetworkInterceptor com métodos reutilizáveis
  • Faça um teste de API puro usando a fixture request

Lidando com Dados

Dados Estratégias
Estratégias para dados de teste
  • .env — para credenciais e URLs por ambiente (nunca hardcode senhas)
  • JSON (dicionário de dados) — para dados estáticos reutilizáveis entre testes
  • APIs — para criar/limpar dados dinamicamente antes de cada teste
  • Mock — para isolar o frontend e simular cenários específicos
  • Combine estratégias conforme a necessidade de cada teste
Quando usar cada estratégia
  • .env: credenciais, tokens, URLs base, feature flags
  • JSON: dados de formulário, listas de produtos, cenários parametrizados
  • API: criar usuário antes do teste, limpar dados no teardown
  • Mock: cenários difíceis de reproduzir, testar erros, isolar frontend
  • Para testes paralelos, cada teste deve ter dados únicos — evite compartilhar
// .env — credenciais e configuração por ambiente
BASE_URL=https://staging.exemplo.com
TEST_USER_EMAIL=qa@exemplo.com
TEST_USER_PASSWORD=SenhaSegura123!
API_TOKEN=token-de-teste-staging

// playwright.config.ts — usando .env
import { defineConfig } from '@playwright/test';
import dotenv from 'dotenv';

dotenv.config();

  use: {
    baseURL: process.env.BASE_URL,
  },

{

  },
  "invalidUser": {
    "email": "invalid@exemplo.com",
    "password": "wrong"

// tests/login.spec.ts — usando dados do JSON
import testData from '../data/users.json';

test('login com dados do dicionário', async ({ page }) => {
  const { email, password } = testData.validUser;
  await page.getByLabel('E-mail').fill(email);
  await page.getByLabel('Senha').fill(password);
});
// utils/api-helpers.ts — criar/limpar dados via API
import { APIRequestContext } from '@playwright/test';

export async function createUser(request: APIRequestContext, data: any) {
  const response = await request.post('/api/users', { data });
  return response.json();
}

export async function deleteUser(request: APIRequestContext, userId: string) {
  await request.delete(`/api/users/${userId}`);
}

// Usando no teste com fixture
test('criar e validar usuário', async ({ page, request }) => {
  // Setup: criar dados via API
  const user = await createUser(request, {
    email: `test-${Date.now()}@example.com`,
    name: 'Test User',
  });

  // Teste: validar na UI
  await page.goto(`/users/${user.id}`);
  await expect(page.getByText(user.name)).toBeVisible();

  // Teardown: limpar dados
  await deleteUser(request, user.id);
});
💡 Para lembrar

A regra de ouro: .env para credenciais, JSON para dados estáticos, API para criar/limpar dados dinâmicos, Mock para isolar e simular cenários. Nunca hardcode senhas ou tokens no código — use variáveis de ambiente.

⚠️ Dados compartilhados causam flaky tests

Quando testes rodam em paralelo e compartilham os mesmos dados (ex.: mesmo usuário, mesmo produto), podem ocorrer conflitos. Cada teste deve criar seus próprios dados ou usar dados únicos gerados dinamicamente (ex.: com timestamp ou Faker.js).

🏠 Para praticar em casa
  • Crie um arquivo .env com credenciais e use no playwright.config.ts
  • Crie um dicionário de dados em JSON e importe em um teste
  • Faça um teste que cria dados via API no setup e limpa no teardown

Integrações com Slack

Integração Notificações
Integração prática com Slack
  • Envie resultados dos testes automaticamente para canais Slack
  • O time recebe notificações quando testes falham na pipeline
  • Use o plugin playwright-slack-report — configuração simples via config
  • Mostra: quantos testes passaram/falharam, duração, link para o relatório
  • Ideal para integrar com fluxo de CI/CD existente
Como funciona
  • Instale: npm install playwright-slack-report
  • Configure como reporter no playwright.config.ts
  • Defina o Slack webhook ou token via variável de ambiente
  • O report é enviado automaticamente após a execução dos testes
  • Personalize a mensagem com informações do projeto
  • Referência: playwrightsolutions.com — Slack messages
// Instalar o plugin
npm install playwright-slack-report

// playwright.config.ts — configuração do reporter Slack
import { defineConfig } from '@playwright/test';

export default defineConfig({
  reporter: [
    ['html'],
    ['playwright-slack-report', {
      channels: ['qa-results', 'dev-team'],
      sendResults: 'always', // 'always' | 'on-failure' | 'off'
      meta: [
        { key: 'Project', value: 'Meu Projeto E2E' },
        { key: 'Environment', value: process.env.ENV || 'staging' },
        { key: 'Build', value: process.env.CI_BUILD_ID || 'local' },
      ],
    }],
  ],
});
// Variáveis de ambiente necessárias
SLACK_BOT_USER_OAUTH_TOKEN=xoxb-your-token-here

// OU usar webhook (alternativa mais simples)
SLACK_WEBHOOK_URL=https://hooks.slack.com/services/T.../B.../xxx

// No CI (GitHub Actions):
env:
  SLACK_BOT_USER_OAUTH_TOKEN: ${{ secrets.SLACK_TOKEN }}
Opções de configuração
  • channels — lista de canais para enviar os resultados
  • sendResults — 'always', 'on-failure' ou 'off'
  • meta — informações extras na mensagem (projeto, ambiente, build)
  • maxNumberOfFailuresToShow — limita quantas falhas são exibidas
  • showInThread — envia detalhes em thread para não poluir o canal
Boas práticas para notificações
  • Use 'on-failure' para evitar spam no canal quando tudo passa
  • Configure canais separados para ambientes diferentes
  • Inclua link para o relatório HTML completo na mensagem
  • Use threads para detalhes — mantenha o canal principal limpo
  • Referência: playwrightsolutions.com — Test results details
💡 Para lembrar

A integração com Slack funciona como um reporter no Playwright — configurada no playwright.config.ts. Você pode ter múltiplos reporters ativos ao mesmo tempo (HTML + Slack + JUnit). O token do Slack deve ser armazenado como secret no CI, nunca no código.
