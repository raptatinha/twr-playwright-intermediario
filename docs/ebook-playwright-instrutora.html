Alinhamento e Boas Práticas Essenciais

20 minutos Teoria + Discussão
O que abordar
  • Revisão rápida da estrutura de um projeto Playwright: tests/, playwright.config.ts, package.json
  • Locators recomendados: getByRole(), getByTestId(), getByLabel()
  • Hierarquia de locators — por que role é preferido sobre css e xpath
  • Anti-patterns comuns: waitForTimeout(), locators frágeis, testes acoplados
  • Referência #1: playwright.dev — "uma das melhores documentações que existem"
  • Princípio: comece simples, refatore quando sentir a dor
Como apresentar
  • Abra o projeto base e mostre a estrutura — conecte com o que já conhecem
  • Demonstre o Pick Locator do VS Code extension para gerar locators
  • Mostre um teste com page.locator('.btn-primary') vs getByRole('button')
  • Liste anti-patterns no quadro/slide e peça exemplos da turma
  • Use exemplos reais de projetos (ex.: Adobe) para engajar
  • Abra a documentação do Playwright ao vivo e navegue com a turma
// ❌ Anti-patterns — locators frágeis
await page.locator('.container > div:nth-child(3) > button.submit').click();
await page.locator('xpath=//div[@class="form"]//input[2]').fill('test');
await page.waitForTimeout(3000); // Nunca faça isso!

// ✅ Boas práticas — locators semânticos
await page.getByRole('button', { name: 'Enviar' }).click();
await page.getByLabel('E-mail').fill('user@test.com');
await page.getByTestId('submit-form').click();

// Hierarquia recomendada de locators:
// 1. getByRole()     → acessível, semântico
// 2. getByLabel()    → formulários
// 3. getByTestId()   → quando não há alternativa semântica
// 4. getByText()     → conteúdo visível
// 5. locator()       → último recurso
💬 Pergunta para engajar

"Quem já teve teste que passava local mas falhava na CI? O que fizeram para resolver?" — Isso abre a conversa sobre boas práticas e conecta com a dor real. Use as respostas para direcionar o foco do workshop.

⚠️ Ponto de atenção

Alunos intermediários podem ter vícios do Selenium/Cypress. Reforce que Playwright tem auto-waiting nativo — não precisa de sleep, waitForTimeout ou esperas manuais. Se o teste precisa de espera explícita, geralmente é sinal de problema no locator ou na lógica.

Page Objects na Prática

25 minutos Teoria + Prática ao vivo
O que abordar
  • O problema: testes duplicados, locators espalhados, manutenção difícil
  • Estrutura simples de Page Object: constructor, locators, métodos de ação
  • Separar ações (métodos que fazem algo) vs validações (métodos assert*)
  • Nomenclatura: sufixo Page, nomes descritivos de locators
  • Quando não usar POM: testes simples, one-off, protótipos
  • Composição: Page Objects podem usar outros Page Objects (componentes)
Demonstração recomendada
  • Mostre um teste "antes" — longo, repetitivo, com locators inline
  • Crie o Page Object ao vivo: LoginPage com constructor e métodos
  • Refatore o teste para usar o POM — compare linhas e legibilidade
  • Adicione método assertLoginSuccess() — separação de responsabilidade
  • Mostre o "antes e depois" lado a lado — momento mais impactante
  • Destaque: se algo muda na UI, só precisa mudar no Page Object
// pages/login.page.ts — Page Object Model
import { type Page, type Locator, expect } from '@playwright/test';

export class LoginPage {
  private readonly emailInput: Locator;
  private readonly passwordInput: Locator;
  private readonly submitButton: Locator;
  private readonly errorMessage: Locator;

  constructor(private readonly page: Page) {
    this.emailInput = page.getByLabel('E-mail');
    this.passwordInput = page.getByLabel('Senha');
    this.submitButton = page.getByRole('button', { name: 'Entrar' });
    this.errorMessage = page.getByRole('alert');
  }

  // Ações
  async goto() { await this.page.goto('/login'); }

  async login(email: string, senha: string) {
    await this.emailInput.fill(email);
    await this.passwordInput.fill(senha);
    await this.submitButton.click();
  }

  // Validações
  async assertLoginSuccess() {
    await expect(this.page).toHaveURL(/dashboard/);
  }

  async assertLoginError(message: string) {
    await expect(this.errorMessage).toContainText(message);
  }
}

// tests/login.spec.ts — Teste usando Page Object
import { test } from '@playwright/test';
import { LoginPage } from '../pages/login.page';

test('login com sucesso', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login('user@email.com', 'senha123');
  await loginPage.assertLoginSuccess();
});
💡 Dica pedagógica

O "antes e depois" é o momento mais impactante. Mostre o mesmo teste com e sem POM lado a lado — os alunos entendem imediatamente o valor. Reforce: "Se a UI muda o label do botão, você muda em um lugar só e todos os testes continuam funcionando."

⚠️ Quando NÃO usar POM

POM não é obrigatório. Em projetos pequenos ou testes exploratórios, locators inline são perfeitamente aceitáveis. A regra de ouro: "Se você está copiando e colando locators entre testes, é hora de criar um Page Object." Comece simples e refatore quando sentir a dor.

Fixtures e Reutilização de Setup

25 minutos Teoria + Prática ao vivo
O que abordar
  • O que são fixtures: setup reutilizável com lifecycle gerenciado
  • Diferença entre test scope (por teste) vs worker scope (por worker)
  • Modelo mental: tudo antes de use() é setup, tudo depois é teardown
  • Compartilhando dados entre testes: fixtures tipadas
  • Custom fixtures: encapsulando Page Objects, dados, configurações
  • Composição de fixtures: uma fixture pode depender de outra
Demonstração recomendada
  • Mostre new LoginPage(page) repetido em 5 specs — qual é o custo?
  • Crie fixture ao vivo com test.extend<MyFixtures>({})
  • Explique o pattern setup → use() → teardown com diagrama
  • Refatore spec para importar test do arquivo de fixture
  • Mostre worker scope: fixture de banco de dados ou servidor
  • Destaque: fixtures são lazy — só executam se o teste pedir
// fixtures/pages.fixture.ts — Custom Fixtures
import { test as base } from '@playwright/test';
import { LoginPage } from '../pages/login.page';
import { DashboardPage } from '../pages/dashboard.page';

type MyFixtures = {
  loginPage: LoginPage;
  dashboardPage: DashboardPage;
};

export const test = base.extend<MyFixtures>({
  // Test scope — criada para cada teste
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await use(loginPage);
    // teardown: limpeza após o teste (opcional)
  },

  dashboardPage: async ({ page }, use) => {
    const dashboard = new DashboardPage(page);
    await use(dashboard);
  },
});

export { expect } from '@playwright/test';

// tests/login.spec.ts — Usando fixtures
import { test, expect } from '../fixtures/pages.fixture';

test('login com sucesso', async ({ loginPage }) => {
  await loginPage.login('user@email.com', 'senha123');
  await loginPage.assertLoginSuccess();
});
💬 Pergunta para engajar

"Quantas linhas de setup vocês têm no beforeEach hoje? Imaginem transformar tudo isso em uma única palavra no parâmetro do teste." — Isso conecta com a dor imediata e mostra o valor das fixtures.

📌 Ponto para destacar

Fixtures são lazy — só executam se o teste declara a fixture como parâmetro. Se nenhum teste pede loginPage, o setup não roda. Isso é diferente de beforeEach, que roda para todos os testes do arquivo indiscriminadamente.

Autenticação e Gerenciamento de Estado

20 minutos Teoria + Demo
O que abordar
  • storageState — salvar cookies e localStorage para reutilizar sessão
  • Login uma vez, reutilizar em todos os testes — economia massiva de tempo
  • Configuração com projects + dependencies no config
  • Cookies e sessão: o que o storageState captura e o que não captura
  • Ambientes diferentes: staging vs production com variáveis de ambiente
  • Múltiplos perfis: admin vs user com JSONs separados
Demonstração recomendada
  • Mostre o config com projects: setup → chromium com dependencies
  • Rode o setup e mostre o JSON gerado em playwright/.auth/
  • Abra o JSON e explique a estrutura (cookies, origins, localStorage)
  • Rode um teste que usa storageState — já começa logado
  • Demonstre o .gitignore incluindo playwright/.auth/
  • Mostre como usar process.env.BASE_URL para ambientes diferentes
// playwright.config.ts — Autenticação com projects
import { defineConfig } from '@playwright/test';

export default defineConfig({
  projects: [
    {
      name: 'setup',
      testDir: './tests/setup',
      testMatch: '**/*.setup.ts',
    },
    {
      name: 'chromium',
      use: {
        browserName: 'chromium',
        storageState: 'playwright/.auth/user.json',
      },
      dependencies: ['setup'],
    },
    {
      name: 'admin',
      use: {
        browserName: 'chromium',
        storageState: 'playwright/.auth/admin.json',
      },
      dependencies: ['setup'],
    },
  ],
});

// tests/setup/auth.setup.ts — Login e salvar estado
import { test as setup } from '@playwright/test';

setup('login como user', async ({ page }) => {
  await page.goto(process.env.BASE_URL + '/login');
  await page.getByLabel('E-mail').fill(process.env.USER_EMAIL);
  await page.getByLabel('Senha').fill(process.env.USER_PASSWORD);
  await page.getByRole('button', { name: 'Entrar' }).click();
  await page.waitForURL('**/dashboard');
  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});
💬 Pergunta para engajar

"Quantos de vocês fazem login no beforeEach de cada teste? Imaginem eliminar isso — cada teste já começa logado, em milissegundos." — Conecta com a dor real e mostra o ganho concreto.

⚠️ Ponto de segurança

Enfatize que os JSONs de storageState contêm tokens de sessão e nunca devem ser commitados no repositório. Mostre como adicionar ao .gitignore. Credenciais devem vir de variáveis de ambiente (.env local, secrets na CI). Feature flags também podem causar divergências entre ambientes — mencione isso como causa comum de flaky tests.

Fluxos Complexos e Múltiplos Contextos

20 minutos Teoria + Demo
O que abordar
  • Multi-page e popups: page.waitForEvent('popup')
  • Multi-step flows: encadear ações complexas com estados intermediários
  • Multi-user: múltiplos browser.newContext() no mesmo teste
  • Context vs Page: quando criar novo contexto vs nova página
  • Cada contexto tem sessão, cookies e storage independentes
  • Casos de uso: chat, permissões admin/user, OAuth popup
Demonstração recomendada
  • Crie dois contextos ao vivo e mostre navegando simultaneamente
  • Demonstre um admin aprovando e um user visualizando a mudança
  • Mostre waitForEvent('popup') com link que abre nova aba
  • Destaque: mesmos métodos funcionam na popup — sem "window handle"
  • Mostre fluxo multi-step: checkout com várias etapas validadas
  • Compare com Selenium: não precisa de switchTo().window()
// Multi-user — admin aprova, user visualiza
const adminContext = await browser.newContext({
  storageState: 'playwright/.auth/admin.json'
});
const userContext = await browser.newContext({
  storageState: 'playwright/.auth/user.json'
});
const admin = await adminContext.newPage();
const user = await userContext.newPage();

// Admin cria um item
await admin.goto('/admin/items');
await admin.getByRole('button', { name: 'Publicar' }).click();

// User vê o item publicado
await user.goto('/items');
await expect(user.getByText('Novo item')).toBeVisible();

// Multi-tab — capturar popup (OAuth, links externos)
const [popup] = await Promise.all([
  page.waitForEvent('popup'),
  page.getByRole('button', { name: 'Login com Google' }).click(),
]);
await popup.getByLabel('Email').fill('user@gmail.com');

// Multi-step flow — checkout com validação de cada etapa
await page.goto('/cart');
await page.getByRole('button', { name: 'Continuar' }).click();
await expect(page).toHaveURL(/checkout\/shipping/);
await page.getByRole('button', { name: 'Finalizar' }).click();
await expect(page.getByText('Pedido confirmado')).toBeVisible();
💬 Pergunta para engajar

"Quem já precisou testar dois usuários ao mesmo tempo — um admin aprovando e um user visualizando? Como resolveram no framework anterior?" — Mostra o cenário real antes de apresentar a solução elegante.

📌 Context vs Page

Novo Context = nova sessão isolada (cookies, storage separados). Use para simular usuários diferentes. Nova Page = nova aba dentro do mesmo contexto (compartilha sessão). Use para multi-tab do mesmo usuário. Essa distinção é fundamental e não existe em outros frameworks da mesma forma.

Network Interception e API

20 minutos Teoria + Demo
O que abordar
  • Interceptar requests com page.route() — o poder de controlar a rede
  • Mockar respostas: route.fulfill() com dados controlados
  • Bloquear requests: route.abort() para eliminar dependências
  • Evitar dependência de backend: testes isolados com mocks
  • Testes de API básicos com request fixture do Playwright
  • Pattern: classe NetworkInterceptor para organizar mocks
Demonstração recomendada
  • Crie um mock ao vivo com page.route() — retorne dados fixos
  • Simule erro 500 e mostre a UI exibindo mensagem de erro
  • Mostre o Promise.all com waitForResponse + ação do usuário
  • Demonstre a classe NetworkInterceptor para organizar mocks
  • Faça um teste de API: POST + validação do response
  • Analogia: "mock é como colocar um ator no lugar do backend"
// Interceptar e mockar resposta de API
await page.route('**/api/products', async (route) => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify([
      { id: 1, name: 'Produto Mock', price: 99.90 },
    ]),
  });
});

// Simular erro do backend
await page.route('**/api/checkout', (route) =>
  route.fulfill({ status: 500, body: 'Internal Server Error' })
);

// Aguardar resposta antes de validar
const [response] = await Promise.all([
  page.waitForResponse('**/api/products'),
  page.getByRole('button', { name: 'Carregar' }).click(),
]);
expect(response.status()).toBe(200);

// Teste de API direto (sem browser)
import { test, expect } from '@playwright/test';

test('POST /api/users', async ({ request }) => {
  const resp = await request.post('/api/users', {
    data: { name: 'Test User', email: 'test@email.com' },
  });
  expect(resp.status()).toBe(201);
  const body = await resp.json();
  expect(body.name).toBe('Test User');
});
💡 Dica pedagógica

Mocks são um conceito novo para muitos alunos. Use a analogia: "É como colocar um ator no lugar do backend — o frontend acha que está falando com o servidor real, mas está recebendo respostas que você definiu." Para a classe NetworkInterceptor, mostre como organiza mocks reutilizáveis entre testes.

⚠️ Equilíbrio mocks vs E2E

Mocks testam frontend isoladamente — são rápidos e estáveis. Mas não substituem testes E2E reais. O ideal é ter ambos: mocks para velocidade e cobertura de cenários de erro, E2E para validar a integração real. Nunca confie 100% em testes que só usam mocks.

Lidando com Dados

15 minutos Teoria + Demo
O que abordar
  • Estratégias para dados de teste: fixtures estáticas vs dinâmicas
  • .env para variáveis de ambiente: URLs, credenciais, flags
  • Dicionário de dados (JSON): massa de teste centralizada e versionada
  • APIs para criação de dados: setup via API antes do teste
  • Mock de dados: quando usar dados fake vs dados reais
  • Independência: cada teste deve criar/limpar seus próprios dados
Demonstração recomendada
  • Mostre um .env com variáveis para diferentes ambientes
  • Crie um test-data.json com dados estruturados
  • Demonstre data factory: gerar dados únicos por execução
  • Mostre setup via API: criar usuário/produto antes do teste E2E
  • Destaque: dados compartilhados entre testes = flaky tests
  • Padrão: usar Date.now() ou UUID para unicidade
// .env — variáveis de ambiente por contexto
BASE_URL=https://staging.meuapp.com
USER_EMAIL=test@email.com
USER_PASSWORD=SenhaSegura123

// data/test-data.json — dicionário de dados centralizado
{
  "users": {
    "admin": { "email": "admin@test.com", "role": "admin" },
    "standard": { "email": "user@test.com", "role": "user" }
  },
  "products": [
    { "name": "Produto A", "price": 99.90, "category": "eletrônicos" },
    { "name": "Produto B", "price": 49.50, "category": "livros" }
  ]
}

// utils/data-factory.ts — Dados únicos por execução
export function createTestUser(overrides = {}) {
  const id = Date.now();
  return {
    email: `test-${id}@example.com`,
    name: `User ${id}`,
    password: 'SenhaSegura123!',
    ...overrides,
  };
}

// Setup via API antes do teste E2E
test.beforeEach(async ({ request }) => {
  await request.post('/api/test/seed', {
    data: { products: [createTestProduct()] },
  });
});
💡 Dica pedagógica

Dados compartilhados entre testes paralelos são a causa #1 de flaky tests. Use o exemplo: "Se dois testes tentam deletar o mesmo produto ao mesmo tempo, um vai falhar." Mostre como dados únicos (Date.now()) eliminam esse problema. Comece simples e escale conforme a necessidade.

📌 Ponto para destacar

Nunca commite credenciais reais no .env. Use .env.example com valores de exemplo no repositório e .env real no .gitignore. Na CI, use secrets do GitHub/GitLab. Para dados sensíveis de teste, considere vault ou variáveis de ambiente da pipeline.

Integrações com Slack

10 minutos Demo prática
O que abordar
  • Por que integrar testes com Slack: visibilidade, feedback rápido
  • Plugin playwright-slack-report — reporter customizado
  • Instalação: npm i -D playwright-slack-report
  • Configuração no playwright.config.ts como reporter
  • Customização: mensagens, canais, filtros de status
  • Alternativas: webhooks manuais, GitHub Actions + Slack
Demonstração recomendada
  • Mostre o plugin instalado e configurado no config
  • Rode os testes e mostre a notificação chegando no Slack
  • Mostre como customizar a mensagem (sucesso vs falha)
  • Destaque: time recebe feedback sem abrir o CI
  • Se não tiver Slack de demo, mostre screenshots do output
  • Mencione: funciona na CI — configure com webhook secret
// Instalação
// npm i -D playwright-slack-report

// playwright.config.ts — Configuração do reporter Slack
import { defineConfig } from '@playwright/test';

export default defineConfig({
  reporter: [
    ['html'],
    [
      'playwright-slack-report',
      {
        channels: ['qa-notifications'],
        sendResults: 'always', // 'always' | 'on-failure' | 'off'
        meta: [
          { key: 'Environment', value: process.env.ENV || 'staging' },
          { key: 'Branch', value: process.env.GITHUB_REF || 'local' },
        ],
        maxNumberOfFailuresToShow: 5,
        slackOAuthToken: process.env.SLACK_BOT_TOKEN,
      },
    ],
  ],
});

// Variáveis de ambiente necessárias:
// SLACK_BOT_TOKEN — token do bot com permissão chat:write
// Configurar como secret na CI (GitHub Actions, GitLab CI)
💡 Dica pedagógica

Esta seção é curta e prática — foque no "wow factor" de ver a notificação chegando no Slack em tempo real. Se não tiver um workspace Slack de demo, prepare screenshots mostrando o resultado. Reforce que isso transforma a cultura do time: "todo mundo sabe quando algo quebra, imediatamente."

📌 Configuração segura

O SLACK_BOT_TOKEN nunca deve estar no código. Use variáveis de ambiente: .env local para desenvolvimento, secrets da CI para produção. Crie um bot dedicado no Slack com permissão mínima (chat:write) e convide-o apenas nos canais necessários.

Q&A e Próximos Passos

Perguntas que costumam surgir
  • "Preciso usar POM em todo projeto?" — Não! Comece simples. Se está copiando locators, é hora de refatorar
  • "Fixture ou beforeEach?" — Fixtures são lazy e tipadas. Use fixtures para setup complexo, beforeEach para coisas simples
  • "Login via UI ou API no storageState?" — API é mais rápido e estável. Use UI só se quiser testar o fluxo de login
  • "Mocks substituem testes E2E?" — Não! Mocks testam frontend isolado. Mantenha E2E para integração real
  • "Como lidar com flaky tests?" — Nunca ignore. Investigue: espera incorreta, dado compartilhado, feature flag, ou bug real
  • "Playwright ou Cypress?" — Playwright: multi-browser, multi-tab nativo, API testing built-in. Escolha o que resolve seu problema
